# Rocker v0.7.0 SFTP Foundation

Date: 2026-09-18
Status: foundation implemented; RC1 candidate prepared separately

This record starts v0.7 on top of the existing Electron SSH connection
authority. The browser preview bridge remains a demo-only fallback and is not
evidence of an SSH or SFTP connection.

## Delivered Foundation

- `electron/sftp/sftp-manager.ts` owns SFTP workspace leases, directory
  operations, path validation, native-file selections, transfer state, progress,
  cancellation, retry, and owner cleanup.
- `electron/sftp/types.ts` defines directory entries, workspace state, selections,
  runtime events, and independent transfer tasks.
- `SshConnectionManager` accepts an `sftp` lease kind. Verified SSH transports
  can be shared by SFTP while terminal and forwarding leases stay independent.
- The typed `RockerBridge`, preload bridge, and IPC registration expose real
  directory and transfer operations. Dialogs run in the main process and all
  requests enforce renderer ownership and input validation.
- `SessionContentView` renders a real file browser route with path navigation,
  parent navigation, new folder, upload, download, overwrite confirmation,
  rename, removal, metadata, drag-and-drop upload, progress, failure,
  cancellation, and retry states.
- The SFTP destination now uses a two-pane workspace: Local is the default
  left pane, while the right pane starts with a host chooser and switches to
  the selected host's real remote file browser.
- Electron's main process lists local directory metadata through a read-only
  owner-checked bridge; the Local pane navigates directories and allows file
  selection for upload. Browser preview rows remain demo-only.
- SFTP has no standalone Sidebar or global overview destination. Users enter
  through a Host action or an existing SFTP Session. The two-pane page has no
  bottom transfer panel; main-process transfer tasks retain their independent
  lifecycle after the visible page closes.
- The local `ssh2` fixture now serves real SFTP directory and file operations;
  integration tests exercise list, mkdir, rename, remove, upload, download,
  overwrite, traversal rejection, and transfer completion after the visible
  workspace closes.

## Lifecycle Contract

An SFTP page owns one workspace lease per host and renderer window. Reopening
the same host in that window reuses the page workspace and its browser state.
Closing the page releases only that workspace lease. A running transfer acquires
its own SFTP lease, so it can continue after page close. The renderer asks before
closing a page with active transfers:

- Continue in background: close the page and keep the task running.
- Cancel: cancel active tasks, wait for their cleanup, then close the page.

Window or renderer-generation cleanup cancels active tasks and releases all
owner leases. This is explicit cleanup, not a claim of restart-safe background
transfers. Tasks are retained in memory for the current owner so completed,
failed, and cancelled results can be rediscovered during the current run.

## Compatibility and Migration

There is no storage schema migration. Old workspace records without `kind`
continue to load as SSH, and existing SFTP browser paths remain compatible.
Transfer tasks are not persisted and are not resumed after application restart.
No credentials, private keys, or remote file contents are written to the
renderer or normal logs.
