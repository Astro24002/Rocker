# Rocker v0.3.1 Reliability Baseline Design

Date: 2026-08-28
Status: Proposed
Scope: Windows and macOS desktop application

## 1. Product Goal

Rocker v0.3.1 makes the existing SSH and terminal foundation dependable for
long-running daily use. The release improves failure handling, makes recovery
behavior visible and actionable, and adds local diagnostics without uploading
user data.

This is a reliability release. It does not add a new SSH protocol capability,
change the overall visual language, or introduce cloud services.

## 2. User Outcomes

- A network interruption does not erase the terminal buffer or block the user
  with a modal dialog.
- A user can see whether a Session is connecting, retrying, disconnected, or
  stopped by an authentication/security/configuration failure.
- Retry and Close actions operate on the existing Session and Connection
  lifecycle; they never bypass the connection manager.
- Security-sensitive failures require an explicit decision and do not retry
  silently.
- A user can export a local, sanitized diagnostic file when support is needed.
- CI validates the real SSH path and refuses to claim a security audit passed
  when the configured registry does not provide an audit endpoint.

## 3. Runtime Architecture

```text
ssh2.Server integration fixture / remote SSH server
                 |
                 v
        SshConnectionManager
        transport + lease owner
                 |
                 v
        TerminalSessionManager
        PTY + generation owner
                 |
                 v
          typed IPC bridge
                 |
                 v
          renderer session state
          overlay + terminal HUD
```

### Ownership

- `SshConnectionManager` is the only owner of SSH clients and connection
  retry policy.
- `TerminalSessionManager` owns PTY channels, channel generations, output
  pumps, and terminal leases.
- `ForwardingManager` owns local listeners and forwarding leases independently
  of terminal sessions.
- Renderer state is a projection of structured events. It must not infer
  network failures from arbitrary error strings or store terminal output.
- Window close, renderer reload, and application shutdown release all
  owner-scoped resources and flush workspace bounds.

## 4. Connection and Terminal State Contract

Connection transport states:

```text
connecting -> ready -> retrying -> ready
connecting -> failed
ready      -> failed
retrying   -> failed
```

Terminal session states exposed to the renderer:

```text
idle
connecting
connected
reconnecting
disconnected
error
closing
```

Failure categories are stable and finite:

```text
network | timeout | dns | authentication |
host-key-changed | host-key-rejected |
configuration | cancelled
```

Automatic reconnect is permitted only for `network`, `timeout`, and `dns`.
Authentication, Host Key, and configuration failures stop recovery and retain
an actionable error state.

The initial `open()` call may wait for a recovery attempt when its first PTY
callback is invalidated by a transport loss. It resolves only after a new PTY
generation is connected, or rejects when recovery is cancelled or fails.

## 5. Failure UX

The existing terminal connection overlay remains the presentation surface.
No global navigation or large visual redesign is required.

| Condition | Presentation | Actions |
| --- | --- | --- |
| Connecting | Non-blocking top status | Cancel |
| Reconnecting | Attempt count and retry state | Reconnect now, Cancel reconnect |
| Disconnected | Static status after recovery stops | Retry, Close |
| Network/timeout/DNS | Preserve xterm buffer | Retry, Close |
| Authentication | Explain that credentials may be invalid | Retry, Close, edit Host entry when available |
| Host Key changed | Security confirmation with old/new fingerprint context | Replace and trust, or Close |
| Host Key rejected | Security error, no automatic retry | Retry, Close |
| Configuration | Specific actionable configuration message | Retry, Close |

Network failures never open a modal dialog. Host Key changes may use the
existing native confirmation dialog because they require an explicit trust
decision. Retry preserves the xterm buffer; Close destroys the logical
Session.

## 6. Local Diagnostics

### 6.1 Collection

The main process records a bounded in-memory event ring and writes local
structured logs under the application data directory. Events include:

- application version, platform, and architecture;
- Session, Connection, and Forwarding lifecycle transitions;
- retry attempts, timing, and terminal state changes;
- sanitized error categories and messages;
- renderer reload and process-gone events;
- build channel and runtime mode.

The logger must not record passwords, passphrases, private-key contents or
paths, complete SSH configuration, terminal input/output, remote file content,
or raw Host Key fingerprints.

Messages are sanitized at the logging boundary, not only during export.
Sensitive values are replaced with stable placeholders before persistence.

### 6.2 Export

For v0.3.1, Export Diagnostics writes one user-selected JSON file. A single
JSON file is deliberate: it is easy to inspect, attach to an issue, and test
without introducing archive dependencies. The format is:

```json
{
  "schemaVersion": 1,
  "metadata": {},
  "events": [],
  "settings": {},
  "lastError": null
}
```

Only a safe settings subset is included: locale, terminal font name and size,
connection timeout, reconnect mode, restore-workspace preference, and bind
address. Credentials and host records are excluded. Export performs a second
sanitization pass and reports the chosen file path to the user. No data is
uploaded automatically.

## 7. Real SSH Integration Tests

The CI-required integration fixture runs an in-process `ssh2.Server` with a
generated host key. It must cover:

- first-use Host Key trust;
- password authentication;
- PTY creation and UTF-8 output;
- input forwarding and PTY resize;
- multiple Sessions reusing one verified connection in one window;
- transport loss, reconnect, and stale channel invalidation;
- authentication failure with no retry;
- Host Key change rejection;
- Session close preventing later recovery.

Tests must use deterministic lifecycle hooks and clean up servers after every
case. They run in the Electron/node Vitest project and do not require a local
sshd installation.

## 8. CI and Quality Gates

The verify job runs:

```text
npm test
npm run typecheck
npm run build
npm audit --omit=dev
```

The audit step must distinguish three outcomes:

- vulnerabilities found: fail;
- audit completed with zero vulnerabilities: pass;
- registry/security endpoint unavailable: fail with an explicit
  `audit unavailable` message, never a false pass.

The configured development registry may remain npmmirror for package
installation. CI security auditing should use an npm registry that supports
the audit API, or fail clearly when that endpoint is unavailable.

## 9. Out of Scope

- SFTP, Snippets, AI, cloud sync, team features, and mobile clients;
- ProxyJump, SOCKS5, remote forwarding, and new SSH authentication methods;
- tmux/screen remote process restoration;
- automatic crash upload or telemetry;
- broad UI restyling or new navigation sections;
- code signing, notarization, and auto-update implementation.

## 10. Acceptance Criteria

The release is accepted when:

1. The real SSH integration suite passes on the CI-supported Node runtime.
2. Network failures preserve terminal content and expose Retry/Close actions.
3. Authentication and Host Key failures stop automatic retry and expose an
   actionable error state.
4. Closing a Session, closing a window, or reloading a renderer releases all
   associated leases and pending waiters.
5. Suspended forwarding remains visible without an active terminal.
6. Diagnostic exports contain no prohibited sensitive data.
7. `npm test`, `npm run typecheck`, and `npm run build` pass.
8. `npm audit --omit=dev` either completes with an auditable result or fails
   explicitly as unavailable.
