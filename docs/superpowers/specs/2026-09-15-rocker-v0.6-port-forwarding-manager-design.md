# Rocker v0.6 Port Forwarding Manager Design

## Status

Proposed design for v0.6.0. The v0.5 renderer already supports discovering
remote listening ports and explicitly starting transient local forwards. This
release turns forwarding into a Host-bound resource manager while preserving
the existing SSH ownership and lease rules.

## Goal

Make local port forwarding dependable and understandable when terminal
sessions are opened, closed, or temporarily disconnected. A saved forwarding
profile belongs to a saved Host. Its runtime listener is independent from any
individual terminal session and may keep the Host's shared SSH transport alive.

## Product Model

The product has two separate forwarding destinations:

1. **Global Port Forwarding page**
   - Entered from the primary navigation.
   - Provides a compact cross-Host overview of existing profiles and runtime
     records.
   - Shows forwarding, suspended, and stopped records.
   - Allows starting or resuming an existing record.
   - Does not provide a create action.

2. **Host-local forwarding page**
   - Belongs to the current Host workspace, alongside that Host's terminal
     sessions.
   - Shows detailed rules for one Host and the relationship between local
     listeners and remote targets.
   - Provides create, edit, start, stop, resume, remove, copy, and open actions.
   - Is reached from the Host workspace or from that Host's Session context
     menu, whose only new item is `Port forwarding`.

These are separate pages/destinations, not two sections of one page. The
global page remains available when no Host Session exists. The Host-local page
is only available after a Host workspace exists.

## Entry And Navigation Rules

### Existing Host Session

The Session context menu gains one item, `Port forwarding`. Selecting it:

- activates the selected Host workspace;
- opens the Host-local forwarding page;
- scopes all displayed rules to that Host.

The action does not create a rule by itself and does not add a separate
terminal tab. The local page contains the create action and may prefill the
selected Host in its editor.

### No Host Session

The global page is still a valid navigation target. It contains no `New
forward` button and no custom-forward form. It can display profiles and
runtime records that were saved previously, including explicitly stopped
records. `Suspended` and `Stopped` records expose a single start/resume action
that re-establishes or reuses a connection for the bound Host and then starts
the listener.

Starting a saved profile from the global page may establish a background SSH
transport; opening a terminal is not required. It must not silently create a
new profile or infer a target from a discovered remote port.

## Resource And Connection Model

```text
Saved Host G11
└── shared verified SSH transport (owner-scoped)
    ├── terminal Session A (independent PTY channel)
    ├── terminal Session B (independent PTY channel)
    └── forwarding profile/runtime (independent listener)
        └── each local socket -> direct-tcpip SSH channel
```

Forwarding reuses the Host's SSH transport, not a terminal's PTY channel and
not one permanent business-level tunnel. Each local client connection creates
its own SSH `direct-tcpip` channel through the shared transport.

The connection reuse key remains the existing identity tuple: application
window owner, `hostId`, resolved address and port, username, authentication
identity, security context, and verified Host Key. A changed Host profile must
not reuse an old transport.

Lifecycle rules:

- Closing one terminal releases only its terminal lease.
- A forwarding runtime keeps its own forwarding lease and listener.
- Stopping a forward closes its listener, releases its lease, and keeps the
  saved profile available as `Stopped`.
- Closing the last terminal does not stop a running forward.
- Closing the owner window stops its runtime forwards and releases leases.
- Transport loss changes running forwards to `Suspended`; loopback forwards
  may recover once when the transport becomes ready.
- Non-loopback forwards require explicit user resume after reconnect.
- A stopped profile is not an active runtime lease. Starting it acquires a
  lease and either reuses a ready transport or establishes one for the Host.

## Data Model

### Persisted Profile

Add a dedicated forwarding profile store. It is separate from workspace
snapshots and transient runtime records.

```ts
type ForwardingProfile = {
  id: string
  hostId: string
  name: string
  description?: string
  localAddress: "127.0.0.1" | "::1" | "0.0.0.0"
  localPort: number
  remoteAddress: string
  remotePort: number
  autoStart: boolean
  createdAt: string
  updatedAt: string
}

type StoredForwardingDocument = {
  version: 1
  profiles: ForwardingProfile[]
}
```

The store normalizes invalid records individually and preserves valid profiles
when one record is malformed. A profile references a Host by id; deleting a
Host removes its profiles after active runtimes are stopped. A profile is
never started implicitly because it was loaded from disk.

### Runtime Record

Extend the runtime forwarding record with `profileId` and `hostId` metadata.
The existing listener/lease state machine remains the owner of active runtime
resources. Runtime records may be listed after they are stopped so the global
page can display restartable records, but `ownerForForwarding` continues to
return no active owner for stopped records.

`ForwardingInfo` returned to the renderer includes:

```ts
profileId?: string
hostId: string
connectionId?: string
```

`connectionId` is present for active/suspended runtime records and may be
absent for a stopped profile. The renderer must not use a connection id as a
persistence key.

## Main-Process Services

### ForwardingProfileStore

Create `electron/storage/forwarding-profile-store.ts` using the same `JsonStore`
health, recovery, diagnostics, and serialized mutation conventions as the
existing stores. Required operations:

- `load()` / `loadWithStatus()`;
- `list(hostId?)`;
- `get(id)`;
- `save(profile)`;
- `remove(id)`;
- `replaceForImport(profiles)` or equivalent atomic mutation;
- `flush()` for shutdown.

### ForwardingManager

Keep `ForwardingManager` as the exclusive owner of local listeners and
forwarding leases. Add profile-aware operations:

- start a profile by `profileId` and Host owner;
- create a runtime from a Host-local quick-create request;
- stop without deleting the profile;
- resume suspended or stopped profiles;
- list profiles joined with runtime state;
- emit stable owner-scoped status events for renderer updates.

To start a profile without a terminal, the manager needs a Host-based acquire
path in `SshConnectionManager`. Add a `kind: "forward"` acquire request that
resolves and verifies the Host, reuses an eligible transport, waits for it to
be ready, and returns a forwarding lease. Existing terminal acquisition
behavior must remain unchanged.

The manager must reject a profile whose Host no longer exists or whose profile
spec is invalid. Local bind conflicts remain actionable as
`LOCAL_PORT_IN_USE`.

### Host Deletion And Window Cleanup

Host removal stops and removes its runtime/profile resources in a bounded
order: stop active runtimes, release leases, then remove profiles. Window
cleanup continues to release runtime forwards independently from terminal
sessions.

## IPC Contract

Keep existing `ports.scan` for remote discovery. Replace renderer assumptions
that `ports.start` requires a connection id with explicit profile-aware calls:

- `ports.listOverview()` - owner-scoped global rows;
- `ports.listForHost(hostId)` - owner-scoped Host-local rows;
- `ports.createProfile(hostId, request)` - save profile, never start;
- `ports.updateProfile(profileId, request)`;
- `ports.removeProfile(profileId)`;
- `ports.startProfile(profileId)` - may establish a background transport;
- `ports.stop(forwardingId)`;
- `ports.resume(forwardingId)` or a single restart operation with clear status;
- `ports.openAddress(forwardingId)`;
- `ports.copyAddress` remains renderer-local clipboard behavior.

The old quick path from a discovered port remains available in the Host-local
page. It creates a profile with a generated name or explicit user name and
then starts it. It is not exposed from the global page.

All profile ids, Host ids, addresses, names, descriptions, and ports are
validated in the main process. Every profile/runtime mutation verifies the
current `RuntimeOwner`. Renderer events are delivered only to the owning
window and include the profile id when available.

## Import And Export

Forwarding profiles are included in sanitized configuration export/import.
Template export contains profiles but no secrets. Encrypted bundle export
contains the same profiles plus existing protected payloads. Import previews
report profile totals and conflicts by stable profile id plus Host binding.

Import never starts a profile. Existing local profiles win by default; the
user may choose keep-local, use-imported, create-copy, or skip for conflicts.
Applying an import uses the existing journal/rollback mechanism so a partial
profile write cannot leave a half-applied configuration.

## Renderer Information Architecture

### Global Page

Use a restrained table or list with these fields:

- Host name and SSH summary;
- local -> remote route;
- state (`Forwarding`, `Suspended`, `Stopped`);
- connection summary (`Shared transport`, `Reconnect required`, or
  `Ready to restart`);
- one contextual action: start/resume, or open the Host workspace.

No create button appears here. Empty state explains that new forwarding rules
are created from a Host Session.

### Host-Local Page

Show the selected Host connection state, terminal Session strip, and detailed
rules. The editor contains profile name, local address/port, remote
address/port, description, and auto-start policy. Non-loopback local binds
show an inline exposure warning. Save and start is available because the page
has an active Host context; save-only remains available for explicit profile
creation.

Do not represent forwarding as a terminal tab. A compact forwarding count or
entry may appear beside the terminal tabs, but the detailed view is a separate
Host workspace destination.

## Error And Recovery Behavior

- Missing/deleted Host: show `Host unavailable` and offer removal of the stale
  profile.
- `LOCAL_PORT_IN_USE`: keep the profile, mark runtime `Error`, and explain how
  to choose another local port.
- Authentication, host-key, or configuration failure: keep the profile in
  `Error`/`Stopped` state without retry loops outside the existing connection
  policy.
- Transport loss: show `Suspended`; expose explicit resume for non-loopback
  rules and automatic one-time recovery for loopback rules.
- Storage blocked: global page remains readable from the current runtime when
  possible, but profile mutations are disabled with the existing storage
  health messaging.

## Testing Strategy

Focused tests are required before broad verification:

- profile store normalization, recovery, flush, Host filtering, and atomic
  replacement;
- Host-based forwarding acquire reuses an eligible transport and creates a
  new one when none exists;
- terminal close does not stop a forwarding runtime;
- stopped profiles remain visible and restartable;
- suspended loopback and non-loopback recovery rules;
- owner/window isolation for profile and runtime IPC;
- profile CRUD validation and Host deletion cleanup;
- import/export preview, conflict resolution, rollback, and no-auto-start;
- global page hides create and exposes restart actions;
- Host-local page creates/edits profiles and quick-forwards discovered ports;
- Session context menu exposes exactly one new `Port forwarding` item;
- English and Simplified Chinese strings for all new visible states/errors.

The release gate remains `npm run typecheck`, the full Vitest suite,
`npm run build`, and `git diff --check`.

## Non-Goals

Remote forwarding, Dynamic SOCKS5, ProxyJump, shared/team forwarding,
automatic forwarding inferred from scans, mobile layouts, and a separate
forwarding application window remain out of scope.

## Acceptance Criteria

1. Global Port Forwarding and Host-local forwarding are separate destinations.
2. The global page works with zero Host Sessions and has no create action.
3. Suspended and stopped profiles are visible globally and can be started or
   resumed.
4. A Session context menu adds only `Port forwarding` and routes to the
   current Host-local page.
5. New profiles are created only in a Host context and are bound to a saved
   Host.
6. Multiple terminal Sessions and forwarding runtimes for one Host share an
   eligible SSH transport while keeping independent channels and lifecycles.
7. Closing a terminal does not stop a retained forward; stopping a forward
   does not close terminal Sessions.
8. Profile import/export is sanitized, versioned, conflict-aware, and never
   starts listeners implicitly.
9. Owner isolation, recovery behavior, accessibility, localization, typecheck,
   tests, build, and diff checks pass.
