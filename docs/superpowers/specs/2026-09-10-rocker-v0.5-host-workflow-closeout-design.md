# Rocker v0.5-A Host Workflow Closeout Design

Date: 2026-09-10
Status: Approved design for implementation planning
Scope: Windows and macOS desktop application

## Goal

Complete the first usable Hosts workflow for v0.5 without expanding the compact
card surface or weakening the existing credential, Host Key, and owner-scoped
SSH boundaries.

This increment is deliberately narrower than the full `v0.5.0 Hosts and Trust`
milestone. It closes Host operations and the current working-tree integration
defects. Trust management remains a separate v0.5-B increment.

## Product Contract

The Hosts route remains a full right-side Workspace. A default Host card shows
only:

1. platform mark;
2. Host label;
3. `SSH · username`.

The card keeps the approved interactions:

- single click selects without connecting;
- double click connects through the existing Session flow;
- hover exposes only the edit icon;
- no three-dot menu, card-level connect button, or always-visible favorite mark.

When a card is selected, a contextual action strip appears in the Hosts header.
The strip contains Edit, Duplicate, Favorite/Unfavorite, and Delete. The strip
is absent when no card is selected. This preserves the compact card design while
making required Host operations discoverable.

The existing search field continues to serve two purposes:

- ordinary text filters saved Hosts;
- a complete `ssh [user@]host [-p port]` command enables the existing Connect
  action and does not change the Host card layout.

Group filters use exact normalized group identity. The current substring
matching behavior is removed so a `Prod` group cannot select `Production`.

## Scope

### Included

- Host save failure propagation from App to HostEditor.
- Safe Host duplication.
- Favorite toggle through the contextual action strip.
- Existing Host deletion exposed through the contextual action strip.
- Exact group filtering.
- Recent Host filter derived from existing successful connection History.
- Typed bridge, preload, mock browser bridge, and renderer tests for the new
  Host operations.
- Main-process mutation serialization and credential cleanup preservation.

### Explicitly Deferred

- Host Key inventory, audit history, and Trust view.
- Tags, environment risk policy, and production-action confirmations.
- Connection test separate from opening a Session.
- Host-level charset/theme consumption by Terminal Sessions.
- Snippet execution or Snippet entity storage.
- Group CRUD and cloud/team synchronization.

## Data and Security Rules

### Duplicate semantics

Duplication is a main-process HostStore operation. It generates a fresh Host
profile ID and never copies credentials by identifier or by value.

The duplicate retains only non-secret connection and display metadata:

- name, with ` copy` appended;
- address, port, and username;
- platform and parent group;
- charset and theme preference fields;
- notes.

The duplicate always uses `authMethod: "agent"`, sets
`publicKeyEnabled: false`, sets `snippetsEnabled: false`, removes
`snippetCollection`, removes `identityFile`, and sets `favorite: false`.
The user must explicitly configure a password or private key in the editor.

### Delete semantics

Deleting a Host removes its profile and clears its protected password and
passphrase through the existing mutation queue. It does not close an already
open Terminal Session; the active Session owns its runtime resources separately.
Future workspace restore ignores the removed Host because the profile is no
longer available.

### Favorite semantics

Favorite is a boolean HostProfile field. Toggling it changes only the profile
metadata and never touches credential storage. No card-level star is rendered in
the default state.

### Recent Host semantics

Recent Hosts are derived in the renderer from existing History records. The
latest unique Host IDs whose outcome is `connected` or `disconnected` are
ordered by `connectedAt`, capped at eight entries, and intersected with the
currently loaded Host profiles. Failed-only records do not appear in Recent.
No second recent-host store is introduced.

## Architecture

### Main process

`HostStore` owns profile mutations:

```ts
list(): Promise<HostProfile[]>
duplicate(id: string): Promise<HostProfile>
setFavorite(id: string, favorite: boolean): Promise<HostProfile>
remove(id: string): Promise<void>
```

`duplicate` creates the sanitized profile described above. `setFavorite` and
`duplicate` run through the existing serialized mutation queue in IPC handlers.
The existing remove handler remains responsible for clearing protected
credentials after the profile mutation.

### IPC and preload

Add typed channels and bridge methods:

```ts
hostsDuplicate: "rocker:hosts:duplicate"
hostsSetFavorite: "rocker:hosts:set-favorite"

hosts.duplicate(id: string): Promise<HostProfile>
hosts.setFavorite(id: string, favorite: boolean): Promise<HostProfile>
```

The handlers validate bounded IDs and booleans, run through the mutation queue,
and return the normalized profile. No renderer code reads the HostStore or
credential store directly.

The browser preview bridge implements the same contract in memory so component
and App tests exercise the production-facing shape.

### Renderer

`HostList` receives the selected Host operation callbacks and a list of recent
Host IDs. The component owns only selection, filter state, and the transient
delete confirmation state. App owns bridge calls and updates the canonical Host
list after a successful operation.

The delete confirmation uses the existing browser confirmation convention used
for multi-line paste, but the message includes the Host label and explains that
protected credentials will also be removed. Cancel leaves selection and card
state unchanged.

App passes `saveHost` directly to `HostEditor` instead of wrapping it in `void`.
HostEditor remains responsible for retaining non-sensitive draft fields and
displaying its existing generic save error after a rejected Promise.

## Error Handling

- Duplicate, favorite, and delete failures leave the selected Host and card list
  unchanged and show a generic inline action error in the Hosts header.
- A duplicate failure never creates a partially visible Host in the renderer.
- A delete failure never clears the card optimistically and never clears
  credentials independently of the profile mutation.
- An unavailable or blocked Host store disables all Host mutation actions while
  keeping navigation, search, and already-open Sessions usable.
- Host IDs, favorite values, and normalized profiles are validated at the IPC
  boundary and again by HostStore normalization.

## Testing Strategy

Tests are written before implementation for each behavior.

### Domain and storage

- duplicate strips identity file, key auth, snippet association, and favorite;
- duplicate preserves safe connection/display metadata and generates a new ID;
- favorite updates exactly one profile;
- missing Host IDs fail without changing the document;
- concurrent duplicate/favorite/remove mutations remain serialized.

### IPC and bridge

- duplicate and favorite handlers reject invalid IDs/booleans;
- handlers invoke HostStore through the mutation queue;
- remove continues clearing both credential kinds;
- returned profiles are normalized and contain no secret values.

### Renderer

- selected card reveals the contextual action strip;
- default cards still contain no favorite marker or three-dot menu;
- favorite toggles through the callback and updates its accessible label;
- duplicate refreshes the list and selects the returned profile;
- delete requires confirmation and leaves the card when cancelled;
- Recent filter orders unique successful History Hosts and caps at eight;
- group filter is exact rather than substring-based;
- App-level Host save rejection leaves HostEditor open with its save error.

### Verification

The increment must pass:

```text
npm run typecheck
npm test
npm run build
git diff --check
```

Native Windows/macOS launch smoke and long soak remain outside the v0.5-A
increment under the existing v0 policy.

## Acceptance Criteria

- A selected Host can be edited, duplicated, favorited, or deleted from the
  contextual action strip without changing single/double-click behavior.
- A duplicate never inherits a password, passphrase, private-key path, private
  key auth mode, Snippet association, or favorite state.
- Delete clears the original protected credentials and leaves existing terminal
  Sessions running.
- Recent Hosts is derived from History and creates no second persistence model.
- Group selection is exact.
- A failed Host save visibly remains in the editor and can be retried.
- Existing SSH connections, Host Key prompts, direct SSH commands, data
  protection, and disabled-storage behavior remain unchanged.

## Follow-up Boundary

After this increment is verified, v0.5-B adds the Trust view through a separate
Host Key inventory and owner-scoped IPC design. It must not be implemented by
adding raw fingerprint inputs or security controls to the compact Host card.
