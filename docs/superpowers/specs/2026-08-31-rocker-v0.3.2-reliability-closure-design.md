# Rocker v0.3.2 Reliability Closure Design

Date: 2026-08-31
Status: Approved design; implementation not started
Scope: Windows and macOS desktop application

## 1. Decision

Rocker v0.3.2 closes the remaining reliability gaps in the v0.3 connection,
terminal, persistence, window ownership, and diagnostics contracts. It is a
bug-fix release. It does not introduce the terminal productivity features
planned for v0.4.0 or the forwarding product features planned for v0.6.0.

The implementation must preserve the existing architecture:

```text
SshConnectionManager
  owns SSH clients, transports, retries, keepalive, and connection leases
              |
              v
TerminalSessionManager
  owns logical Sessions, PTY generations, output pumps, and attempt cancellation
              |
              v
typed owner-scoped IPC
              |
              v
renderer Session projection + xterm.js buffer
```

The release is complete when the known reliability defects have deterministic
regression coverage, the 30-minute soak passes, and the existing Windows and
macOS release pipeline remains green.

## 2. Goals

- Cancel a connecting or reconnecting Session immediately without waiting for
  the SSH ready timeout.
- Keep cancellation scoped to one logical Session when a verified SSH
  Connection is shared by other consumers.
- Make PTY creation deterministic when a transport is lost while the shell
  callback is still pending.
- Detect silent dead transports with SSH keepalive and retain the existing
  reconnect policy.
- Classify local key, agent, credential, and configuration failures correctly
  so they never enter network auto-retry.
- Prevent local JSON read-modify-write races and preserve a last-known-good
  backup.
- Prevent failed bootstrap from overwriting an existing workspace with empty
  renderer state.
- Isolate resources from an old renderer generation during reload cleanup.
- Bound remote monitoring operations and keep their failures independent from
  transport health.
- Complete the v0.3 diagnostics contract without recording sensitive content
  or paths.
- Enforce one Electron main process while retaining multiple application
  windows.

## 3. Non-Goals

- Terminal search, Command Palette, shortcut configuration, terminal context
  menus, or other v0.4.0 productivity work.
- Host groups, tags, Security Center, or other v0.5.0 work.
- Saved forwarding profiles, non-loopback exposure UX, Remote Forward,
  Dynamic SOCKS5, or other v0.6.0 work.
- SFTP, Snippets, AI, cloud sync, team features, or mobile clients.
- A global reliability supervisor that takes ownership away from the existing
  managers.
- Cross-process file locking. A single Electron main process is the file
  ownership boundary.
- Restoring a dead remote shell process. Reconnect creates a new PTY and keeps
  the local xterm buffer only.
- Making an eight-hour test a v0.3.2 per-commit gate. Eight-hour continuous use
  remains a whole-product dogfooding objective.

## 4. System Invariants

The implementation must maintain all of these invariants:

1. `SshConnectionManager` is the only owner of SSH Client instances, transport
   retry timers, keepalive configuration, and connection records.
2. `TerminalSessionManager` owns logical Session state, PTY channels, output
   pumps, and one cancellation controller per active attempt.
3. `ForwardingManager` owns forwarding listeners and forwarding leases
   independently from Terminal Sessions.
4. React never accumulates terminal output. xterm.js remains the terminal
   buffer owner.
5. One Session cancel or close never releases another consumer's connection
   lease.
6. Connection reuse still requires the same owner window, host configuration,
   authentication identity or credential, and verified Host Key.
7. Only `network`, `timeout`, and `dns` failures can auto-retry.
8. A renderer generation can release only resources that were acquired by
   that same generation.
9. A failed or blocked store load never opens the write gate for that store.
10. Diagnostics observe lifecycle events but never control product behavior.
11. Cleanup, diagnostic recording, and renderer event delivery failures never
    replace the original business error.
12. Every asynchronous operation settles at most once.

## 5. Ownership Model

### 5.1 Owner scope

Runtime resources use an internal owner value:

```ts
interface RuntimeOwner {
  webContentsId: number
  rendererGeneration: number
}
```

`RuntimeOwner` is created and resolved by the Electron main process. Renderer
payloads never supply a trusted generation value. IPC handlers derive the
current owner from `event.sender` through `WorkspaceWindowManager`.

Connection records, connection leases, Terminal Session records, forwarding
records, restore admissions, and pending waiters are indexed or tagged with the
full owner value. Equality requires both fields to match.

### 5.2 Renderer lifecycle

`WorkspaceWindowManager` maintains a monotonically increasing generation for
each `webContentsId`:

```text
first completed load       -> generation 1
reload completed           -> generation 2
next reload completed      -> generation 3
```

When a completed renderer begins reloading or its process exits, the manager
captures the previous owner and starts cleanup for that exact owner. New IPC
requests are not admitted until the new generation is registered. A late
cleanup from generation N cannot match resources created by generation N+1.

Closing the native Window releases every remaining generation associated with
its `webContentsId`. Window close is the only operation allowed to use this
broader cleanup.

Before sending a Session event, main verifies that the target Window exists,
is not destroyed, and still owns the event's generation. A send failure is
recorded as a safe diagnostic event and is otherwise ignored.

### 5.3 Single main process

Rocker acquires `app.requestSingleInstanceLock()` before `app.whenReady()` and
before any store is opened. A process that does not obtain the lock exits
without initializing storage or runtime managers.

The primary process handles `second-instance` by restoring, focusing, and
bringing the most recently active Rocker Window to the front. If the primary
process has no Window, it creates one through `WorkspaceWindowManager`.
Multiple Windows continue to run inside the single main process.

## 6. Connection and Terminal Attempt Contract

### 6.1 Attempt identity

Each initial open, manual Retry, or automatic recovery creates one internal
attempt:

```ts
interface TerminalAttempt {
  attemptId: number
  controller: AbortController
  expectedTransportGeneration?: number
  expectedChannelGeneration: number
}
```

`attemptId` increases monotonically within a logical Session. Creating a new
attempt aborts and retires the previous attempt before any asynchronous work is
started.

The internal connection request accepts a cancellation signal:

```ts
interface ConnectionAcquireRequest {
  hostId: string
  owner: RuntimeOwner
  kind: "terminal"
  forceNewConnection?: boolean
  signal?: AbortSignal
}
```

The signal is a main-process implementation detail and is not serialized over
IPC.

### 6.2 Normal open

```text
Session connecting
  -> acquire(signal)
  -> Connection ready
  -> open PTY(signal, transportGeneration)
  -> validate attempt + transport generation
  -> install output pump
  -> increment channelGeneration
  -> Session connected
```

An acquired lease is assigned to the Session only while the attempt is still
current. If the attempt was invalidated while acquire was pending, the returned
lease is released before the attempt settles.

### 6.3 Cancel and close

Cancel is authoritative and synchronous at the logical state boundary:

```text
Cancel
  -> recoveryDesired = false
  -> abort current attempt
  -> reject initial-open and recovery waiters with cancelled
  -> release this Session lease
  -> emit disconnected/cancelled once
  -> retain logical Session and xterm buffer
```

If the cancelled request is the only waiter or lease on a connecting record,
`SshConnectionManager` cancels its timeout and retry timer, ends the SSH Client,
and removes the record. If other waiters or leases exist, it removes only the
cancelled request and leaves the shared transport running.

Retry creates a new attempt on the existing logical Session. Close performs the
Cancel behavior and then removes the logical Session, PTY, output pump, and
renderer xterm instance.

A late ready, error, close, shell callback, retry timer, or output event from an
aborted attempt is ignored after its local resources are released.

### 6.4 PTY and transport race

The shell callback validates all of the following before installing a channel:

- the logical Session still exists;
- the attempt is current and not aborted;
- the connection id is unchanged;
- the transport generation is unchanged;
- the Session still desires recovery.

If the transport becomes invalid while `client.shell()` is pending, both a
successful late channel and a callback error are normalized to
`TerminalStartInvalidatedError`. A successful late channel is ended immediately.

When recovery remains permitted, the initial `open()` waits for the next ready
transport and resolves only after a new PTY generation is connected. It rejects
only when recovery is cancelled, reaches a terminal failure, or the logical
Session is closed. This prevents an `open()` rejection from coexisting with a
renderer Session that is still reconnecting.

### 6.5 Keepalive and retry

Production SSH clients use:

```ts
keepaliveInterval: 15_000
keepaliveCountMax: 3
```

Keepalive remains active while the Connection has at least one Terminal or
Forwarding lease, including while the application is in the background. Three
consecutive missed responses classify the transport loss as `network`; normal
connection backoff then applies.

User-disabled Auto Reconnect suppresses retry after transport loss but does not
disable keepalive detection. Authentication, Host Key, configuration, and
cancellation failures never schedule a retry.

## 7. Failure Model

Failure domains remain distinct:

```ts
type ConnectionFailure =
  | "network" | "timeout" | "dns" | "authentication"
  | "host-key-changed" | "host-key-rejected"
  | "configuration" | "cancelled"

type StorageFailure =
  | "corrupt" | "permission" | "unavailable" | "recovery-failed"

type RemoteOperationFailure =
  | "timeout" | "cancelled" | "output-limit" | "channel-error"
```

Raw Node, filesystem, socket, and ssh2 error strings are mapped in main. The
renderer consumes typed reason values and safe bounded messages; it never
infers state from English error text.

Private-key `ENOENT`, `EACCES`, missing paths, unsupported key formats, missing
agent endpoints, and safeStorage access failures map to `configuration`. They
do not enter automatic retry.

Network, timeout, and DNS failures preserve the xterm buffer and expose Retry
and Close through the existing Terminal overlay. Cancelled becomes a normal
disconnected state, not a red error. Host Key changed or rejected remains on
the existing explicit security path and cannot be bypassed by generic Retry.

Duplicate presentation is suppressed by operation id, reason, and lifecycle
generation. Expected cancellation caused by renderer reload or Window close is
not presented to the user.

## 8. Persistence Contract

### 8.1 Load result

Store adapters return an explicit result:

```ts
type LoadResult<T> =
  | { status: "ok"; value: T }
  | { status: "recovered"; value: T; source: "backup" }
  | { status: "defaulted"; value: T; reason: "missing" | "corrupt" }
  | { status: "blocked"; issue: StorageIssue }
```

The generic JSON layer owns file integrity. Individual adapters own schema
normalization and the decision between defaulting and blocking.

### 8.2 Mutation serialization

Each store instance has one promise-based mutation queue. Update operations
enqueue the complete read-current, normalize, modify, and write transaction.
Callers do not implement independent read-modify-write sequences.

The one-main-process rule guarantees one in-memory queue per application data
file. Different files retain independent queues and may be updated in parallel.

### 8.3 Atomic write and backup

For `<name>.json`, a write uses this sequence:

1. Serialize and validate the complete next document in memory.
2. Write it to a unique same-directory temporary file containing the process
   id and an incrementing operation id.
3. Flush and close the temporary file.
4. If the current primary parses and validates, copy it to a unique backup
   temporary file and atomically replace `<name>.json.bak`.
5. Atomically replace the primary with the new temporary file.
6. On a first successful write with no backup, copy the validated new primary
   into `<name>.json.bak`.
7. Remove abandoned temporary files owned by the completed operation.

An invalid primary never replaces a valid backup. A failed write leaves either
the old primary or the new primary intact and reports a bounded storage error.

Credentials remain encrypted by Electron safeStorage in the primary, backup,
and quarantine copies. On systems with POSIX permissions, Rocker requests mode
`0600` for sensitive store files and best-effort owner-only directory access.
Windows continues to rely on the user profile ACL and safeStorage encryption.

### 8.4 Corruption recovery

When a primary cannot be parsed or validated, Rocker moves it to a unique UTC
timestamped quarantine path such as:

```text
settings.20260831T142530123Z.corrupt
```

Name collisions receive an incrementing suffix. Rocker never overwrites or
automatically deletes quarantine files.

Recovery policy:

| Store | Valid backup | No valid backup |
| --- | --- | --- |
| Settings | Recover backup | Use default settings |
| History | Recover backup | Use empty history |
| Workspace | Recover backup | Use empty workspace |
| Hosts | Recover backup | Block host operations |
| Credentials | Recover backup | Block credential operations |
| Host Keys | Recover backup | Block SSH trust operations |

Missing files are normal first-run state. They use safe defaults and are not
quarantined. Permission and I/O failures never masquerade as missing or corrupt
files; they return `blocked` unless an already validated in-memory snapshot can
continue read-only operation.

## 9. Bootstrap and Degraded Operation

Renderer bootstrap has explicit states:

```text
loading
  -> ready
  -> degraded/recoverable
  -> degraded/blocked
```

Hosts, History, Settings, and Workspace are loaded independently so one
non-security store failure does not hide the status of the others. Credentials
and Host Keys are reported as dependency health without sending their contents
to the renderer.

Each persisted renderer document has a write gate. The Workspace gate opens
only after Workspace load returns `ok`, `recovered`, or `defaulted`. A rejected
IPC call, cancelled bootstrap, blocked result, or unexpected initialization
error keeps the gate closed. React state changes while the gate is closed never
invoke workspace save.

The application stays open in degraded mode:

- a compact non-modal banner identifies the unavailable data category;
- `Retry` reruns only failed store loads;
- `Export diagnostics` remains available;
- Local Terminal and unaffected Settings remain usable;
- SSH open and reconnect are disabled when Hosts, Credentials, or Host Keys are
  blocked;
- recovered/defaulted notifications disappear after acknowledgement or a short
  display period;
- blocked notifications remain until recovery succeeds.

Security-data failures state explicitly that Rocker did not reset the data.
There is no one-click destructive reset in v0.3.2.

## 10. Bounded Remote Operations

Connection-scoped command execution accepts an internal policy:

```ts
interface RemoteExecOptions {
  timeoutMs: number
  maxOutputBytes: number
  signal?: AbortSignal
}
```

Monitoring uses `timeoutMs: 8_000` and `maxOutputBytes: 262_144`. The executor
listens for the exec callback error, channel error, close, timeout, cancellation,
and output growth. A once-settlement guard prevents any second outcome.

On timeout, cancellation, channel error, or output limit, the executor closes
the channel and removes all operation listeners. The operation error affects
only the current monitoring sample. It does not mark the shared SSH transport
failed; transport health is determined by SSH Client events and keepalive.

The monitoring HUD marks unavailable metrics as stale for that sample and
tries again on its normal schedule. It does not show a global application
error for an isolated monitoring failure.

## 11. Diagnostics

The existing local, bounded, fail-open diagnostic logger remains the only
diagnostic sink. v0.3.2 adds structured events for:

- application version, platform, architecture, build channel, and runtime mode;
- renderer load, reload, process-gone, and Window close;
- storage recovered, defaulted, blocked, and retry outcome;
- connection acquire cancelled and transport lost;
- PTY attempt invalidated and recovery outcome;
- monitoring timeout, output limit, and channel error;
- owner cleanup start and completion using safe internal identifiers.

Events use finite action and reason values. They do not record hostname,
username, command text, terminal input/output, raw Host Key fingerprints,
credential content, private-key content, or complete configuration.

Sanitization is applied when recording and again when exporting. Sensitive key
matching explicitly rejects password, passphrase, private key, `identityFile`,
agent endpoint, SSH config, fingerprint, terminal content, remote file content,
and any filesystem path. Raw error objects are never serialized.

The logger keeps its existing bounded event ring and JSONL recovery behavior.
A record, flush, export, or event-send failure is caught and cannot interrupt a
Session, Connection, store recovery, or shutdown.

## 12. Test Strategy

### 12.1 Deterministic unit and manager tests

Tests must prove:

- cancelling a connecting Session rejects its open waiter promptly without
  waiting for the SSH ready timeout;
- cancelling the only waiter ends its SSH Client once and prevents a late ready;
- cancelling one waiter on a shared Connection leaves other consumers ready;
- transport loss interleaved with a PTY callback waits for the recovered PTY;
- stale PTY callbacks, output, resize, and ready events are generation-guarded;
- private-key `ENOENT` and `EACCES` are configuration failures with no retry;
- production keepalive defaults are 15 seconds and three missed responses;
- remote exec timeout, cancellation, channel error, and output limit settle once
  and close their channel;
- concurrent mutations on every generic JSON-backed adapter lose no updates and
  create no temporary-file collision;
- valid backup, invalid backup, missing file, corrupt file, permission error,
  and failed atomic replacement follow the store policy table;
- a failed bootstrap never invokes workspace save;
- cleanup for renderer generation N cannot release generation N+1 resources;
- a second application instance does not initialize storage;
- diagnostic record and export sanitization remove every prohibited field.

### 12.2 Real SSH integration fixture

The in-process `ssh2.Server` fixture is extended with deterministic hooks for:

- delaying handshake/authentication so cancellation can be observed;
- delaying a shell callback while dropping the transport;
- ignoring keepalive requests with a test-only short keepalive policy;
- tracking PTY generations, resize, input, and stale output;
- opening two Terminal Sessions and one Forwarding consumer on one verified
  Connection;
- reporting open channels and listeners during cleanup.

Integration tests cover handshake cancellation, PTY-open transport loss,
single-consumer cancellation on a shared Connection, keepalive detection and
single recovery, stale channel invalidation, and owner close. After cleanup,
Sessions, Connections, leases, listeners, timers, and pending waiters must all
equal zero.

Production keepalive values are tested separately from accelerated fixture
values so the suite remains deterministic and fast.

### 12.3 Thirty-minute soak

`npm run test:soak` runs outside ordinary per-commit CI and repeatedly performs:

```text
open two Sessions
stream UTF-8 output
resize PTYs
execute a monitoring sample
drop the transport
recover the Connection and PTYs
close one Session
close the owner Window
```

After every owner close, all manager resource counts must return to the exact
baseline. The first five minutes are warm-up. The median process RSS during the
last five minutes must not exceed the median from minutes five through ten by
more than 25 percent. The test also fails on uncaught rejection, duplicate
settlement, stale output acceptance, or a continuously growing manager count.

The soak emits a machine-readable summary containing iteration count, failure
count, reconnect count, maximum resource counts, and memory medians. It contains
no terminal content or connection secrets.

## 13. Release Acceptance

The v0.3.2 release candidate is accepted when:

1. All deterministic tests in this design pass.
2. The real SSH integration suite passes on the CI-supported Node runtime.
3. `npm test`, `npm run typecheck`, and `npm run build` pass.
4. Production dependency audit completes against the official npm registry with
   an auditable result; an unavailable audit endpoint fails explicitly.
5. The 30-minute soak meets resource and memory criteria.
6. Windows and macOS installers each complete one launch, SSH connect, transport
   reconnect, Session close, and application close smoke test.
7. Closing or reloading a Window leaves no owned lease, listener, timer, channel,
   or pending waiter.
8. A corrupt or unavailable store cannot be overwritten by empty bootstrap
   state.
9. Diagnostic export tests contain no prohibited sensitive data.
10. The Release workflow still publishes only the six allow-listed x64/arm64
    Windows and macOS assets.

## 14. Version Boundary

v0.3.2 is finished by correcting the established reliability contract, not by
adding visible productivity scope. After these acceptance criteria pass,
v0.4.0 can build Terminal Search, Command Palette, configurable shortcuts,
terminal context actions, scrollback/cursor settings, Session ordering, and
improved recovery affordances on a closed reliability baseline.
